1. Зачем проекту история

Представь, что ваша команда делает сервис заявок на ремонт компьютеров. В понедельник вы решили, что в форме достаточно описания проблемы. Во вторник лаборант получил заявку «Монитор не включается» и не смог найти нужный компьютер. В среду команда добавила требование указывать кабинет. Через месяц вас спрашивают, когда и зачем оно появилось. Текущая версия файла показывает новое правило. Чтобы ответить на вопрос, нужна история изменения.

Можно складывать копии в файлы вроде требования_новые_точно.md. Для одного документа это иногда помогает. В проекте с кодом, тестами и инструкциями приходится ещё помнить, какие версии файлов работали вместе. Система контроля версий позволяет сохранить согласованное состояние проекта, дать изменению имя и позже увидеть, какие строки в него вошли.

Такая история полезна, когда разработчик ищет, после какой правки сломалась проверка формы, преподаватель смотрит, как менялось решение задачи, или команда уточняет, почему ввела новое правило. Git работает и с программой на Java, и с текстом требований. На этой лекции начнём с одного файла, чтобы видеть все изменения целиком.

2. Где здесь Git, GitHub и GitHub Pages

ИнструментЧто делаетГде пригодится
GitВедёт историю файлов проекта и позволяет сравнивать версии.На компьютере разработчика, в том числе без подключения к сети.
GitHubРазмещает репозитории и даёт команде общее место для обсуждения правок.Когда несколько человек работают над одним проектом или хотят поделиться исходниками.
GitHub PagesПубликует статические страницы проекта как сайт.Например, чтобы всю группу пустить к этому учебнику по одной ссылке.

Вопрос перед демонстрацией. В аудитории отключили Интернет. Можно ли сохранить очередную версию проекта? Да, если Git установлен и проект открыт локально. Отправить новую версию на GitHub можно после восстановления связи.

3. Три места, где может находиться правка

  1. Рабочая папка. Здесь лежат файлы, которые ты открываешь и редактируешь. Сохранение в редакторе записывает новое содержимое файла.
  2. Подготовленные изменения, или индекс. Команда git add помещает выбранное содержимое в будущий коммит. После новой правки можно снова выполнить git add, чтобы обновить подготовленную версию.
  3. История репозитория. Команда git commit фиксирует подготовленное состояние. У коммита есть идентификатор, данные автора и сообщение о правке.

Сохрани файл → посмотри изменения → подготовь нужное через git add → проверь подготовленное → сделай git commit.

Представь, что в README добавили правило про кабинет и выполнили git add README.md. Потом в тот же файл добавили ещё одну строку про фотографию. Если сейчас сделать коммит, в него попадёт подготовленная версия с кабинетом. Строка про фото останется в рабочем файле. Так Git позволяет отделить законченную правку от той, над которой ещё работают. Pro Git о записи изменений.

4. Демонстрация. Создаём первую версию

Открой Git Bash на Windows. Команды вводи по блокам. Если папка op03-git-demo уже существует, используй другое свободное имя в первых двух строках второго блока. Кнопки копирования берут только команды.

Шаг 1. Проверить Git и создать репозиторий

git --version

Должна появиться строка, начинающаяся с git version. После этого создай отдельную учебную папку. Последние две команды задают учебного автора только в этом репозитории. Эти данные нужны для подписи коммитов.

mkdir op03-git-demo
cd op03-git-demo
git init -b main
git config --local user.name "Student Demo"
git config --local user.email "student@example.test"

Что увидишь. Git сообщит, что создал пустой репозиторий. Служебная история хранится в скрытой папке .git внутри проекта. main — имя начальной ветки, то есть основной линии разработки в этом примере.

Шаг 2. Создать README и прочитать статус

README — файл, с которого удобно начинать знакомство с проектом. В нём обычно пишут, что делает проект и как с ним работать. Для примера возьмём короткий заголовок на английском, чтобы команды можно было одинаково выполнить на всех учебных компьютерах.

printf '%s\n' '# Service desk' > README.md
git status --short
?? README.md

?? означает, что файл есть в папке и Git пока его не отслеживает. Символ > в команде создаёт файл с указанным содержимым. На следующих шагах >> будет добавлять строку в конец существующего файла.

Шаг 3. Подготовить файл и сделать первый коммит

git add README.md
git status --short
git commit -m "Add project overview"

После git add статус покажет A  README.md: новый файл подготовлен. После git commit Git напечатает сообщение Add project overview и идентификатор коммита. Сообщение отвечает на вопрос «что изменилось?». Через месяц по нему проще найти нужную правку, чем по подписи «готово».

5. Добавляем правило и проверяем, что именно изменилось

Лаборанту нужно знать, куда идти. Добавим в README правило «В заявке должен быть номер кабинета».

printf '%s\n' 'A ticket must include a room number.' >> README.md
git --no-pager diff -- README.md

В выводе будут служебные строки с именами файла и номерами строк. Саму правку можно узнать по плюсу в начале строки:

+A ticket must include a room number.

Сейчас git diff показывает, что изменилось в рабочем файле по сравнению с подготовленной версией. После git add та же строка станет частью будущего коммита. Чтобы проверить его содержимое перед фиксацией, используем git diff --staged.

git add README.md
git --no-pager diff --staged -- README.md
git commit -m "Require a room number"
git --no-pager log --oneline
git status --short

Контроль результата. В истории две записи, последняя по времени сверху. Начальные символы ниже условные. На твоём компьютере идентификаторы будут другими. Последний git status --short ничего не выводит, потому что после коммита новых правок в учебной папке нет.

7fd10b2 Require a room number
2b91c6a Add project overview

Чтобы ответить на исходный вопрос о том, когда появилось требование, можно открыть последний коммит. В выводе будут сведения о коммите и добавленная строка.

git --no-pager show HEAD -- README.md

HEAD в этом примере указывает на текущий коммит. По коммиту можно доказать, что в выбранный момент появилось правило про кабинет. Причину правки команда может дополнительно записать в описании задачи: «Лаборант не может найти компьютер без номера кабинета».

6. Если результат отличается

Что видишьЧто проверить
git: command not foundУстановлен ли Git и открыт ли Git Bash.
not a git repositoryПокажи текущую папку командой pwd. Перейди в учебную папку, где выполнил git init.
Author identity unknownПовтори две строки git config --local из шага 1 в учебном репозитории, затем повтори коммит.
no changes added to commitПосмотри git status --short. Если нужный файл изменён в рабочей папке, подготовь его через git add README.md.
git diff ничего не показывает сразу после git addОткрой git diff --staged. Если правка уже зафиксирована, её видно через git show HEAD.

При работе с настоящим проектом просматривай изменения перед фиксацией. В учебный репозиторий помещай вымышленные данные. Пароли, токены и реальные заявки с персональными данными храни отдельно от публикуемого проекта.

7. Самопроверка и отчёт

Сначала ответь своими словами, затем открой разбор.

Ты сохранил README в редакторе. Появилась ли новая запись в истории?

Запись появится после успешного коммита. Сохранение в редакторе пока изменило рабочий файл. Можно увидеть правку через git diff, подготовить её и зафиксировать.

После git add ты добавил ещё одну строку. Куда она попадёт?

Она останется в рабочем файле. Следующий коммит возьмёт уже подготовленную версию. Чтобы добавить и эту строку, повтори git add README.md и проверь git diff --staged.

Как показать одногруппнику, какой коммит добавил номер кабинета?

Найди по git log --oneline коммит Require a room number. Открой его через git show с его идентификатором и покажи строку с плюсом. Если это текущий коммит, подойдёт git show HEAD.

Мини-отчёт после демонстрации. Запиши цель, вставь вывод git log --oneline с двумя своими коммитами и фрагмент git show HEAD -- README.md с добавленной строкой. В выводе своими словами объясни, зачем хранить такое изменение в истории проекта. Например: «Я нашёл коммит, в котором появилось требование про кабинет. В командном проекте так можно проверить, когда изменилось правило ввода заявки».

8. Коротко под запись

Репозиторий — проект с историей версий. Коммит — запись подготовленного состояния в истории. git status показывает состояние файлов, git diff — правки рабочей папки относительно индекса, git diff --staged — подготовленные правки, git log — историю. На следующей лекции используем эту же папку, чтобы попробовать изменения в отдельной ветке.
