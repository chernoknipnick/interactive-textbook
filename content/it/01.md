## 01. Что такое информационная технология

**Цель пары.** Научиться узнавать информационную технологию в знакомом сервисе, объяснять её назначение и различать три уровня классификации. В конце занятия ты сможешь обосновать наблюдение из ПР01.

<details markdown="1">
<summary>План занятия на 90 минут</summary>

1. **10 минут.** Обсудить сообщение о неисправном мониторе и выяснить, каких сведений не хватает лаборанту.
2. **20 минут.** Разобрать компоненты технологии и проследить путь заявки по таблице.
3. **20 минут.** Сопоставить глобальный, базовый и конкретный уровни на примерах сервиса заявок и электронной очереди.
4. **25 минут.** В парах разобрать наблюдение из ПР01 и составить три колонки отчёта. Если исходный отчёт недоступен, использовать пример с расписанием.
5. **15 минут.** Обсудить границы выводов и ответить на вопросы самопроверки.

</details>

### Зачем сервису технология

Представь компьютерный класс. Студент сообщает в чат: «Монитор не включается». Лаборант читает сообщение через час, уточняет кабинет и просит назвать номер компьютера. К вечеру сообщение теряется среди других. Через неделю никто не помнит, кто взялся за ремонт. Сообщение было передано, но его дальнейший путь никто не определил.

**Информатика** изучает способы представления, передачи, хранения и обработки информации. **Информационная технология** — организованный способ работать с информацией для конкретной цели. В сервисе заявок эта цель — довести сообщение о проблеме до человека, который её устранит, и сохранить результат. Для этого нужны технические средства (компьютеры, сеть), программные средства (браузер, приложение) и процедуры (какие поля заполняет студент, кто берёт задачу, как фиксируется ремонт).

### Три уровня классификации

Уровень выбирают по роли технологии. Одна система может использовать все три.

<ol class="levels" aria-label="Три уровня информационных технологий">
<li class="global"><strong>1. Глобальный</strong><p>Инфраструктура для многих систем. Интернет связывает узлы сети.</p></li>
<li class="base"><strong>2. Базовый</strong><p>Общий способ работы. Веб-технологии передают запросы, базы данных хранят записи.</p></li>
<li class="concrete"><strong>3. Конкретный</strong><p>Прикладное решение. Сервис заявок учитывает неисправности и показывает статус ремонта.</p></li>
</ol>

Назначение — отдельный признак классификации. Электронный журнал относится к образовательным технологиям по области применения и к **конкретным технологиям**{:.concrete} по уровню. База данных может лежать в основе и журнала, и склада. В обоих случаях это **базовая технология**{:.base}. При классификации сначала спрашивай, общая ли это инфраструктура, переиспользуемый способ или решение прикладной задачи.

### Как связать с уже выданной ПР01

Возьми одно наблюдение из DevTools. Например, на вкладке Network появился запрос, а в Response виден JSON с данными. Это свидетельство обмена между программами. Запиши три колонки: «что увидел», «как классифицировал», «почему». Образец: «Браузер запросил список заявок и получил JSON → **базовый уровень**{:.base} → веб-обмен используется также в журналах и интернет-магазинах». По одному JSON невозможно установить, какая СУБД стоит за сервером. Для отчёта достаточно уверенно объяснить наблюдаемое.

### Из чего складывается технология: разбор одной заявки

До появления карточки у нас есть наблюдение человека. Студент формулирует проблему, выбирает кабинет и сообщает номер компьютера. Это **исходные данные**{:.source}. Описание «чёрный экран после включения» помогает лаборанту подготовиться, а номер компьютера указывает, какой именно аппарат проверить. При сохранении приложение присваивает карточке номер 101. Номер становится ссылкой на обращение для всех участников.

Дальше работают три компонента. **Технический** обеспечивает ввод, передачу и хранение: клавиатура, компьютер, сеть и серверное оборудование. **Программный** даёт форму, проверку полей и список обращений. **Организационный** задаёт, кто вводит данные, кто может принять заявку и что считается её закрытием. Для результата важна связка. Например, форма позволяет нажать «Закрыть», а процедура требует сначала записать, что было сделано. Приложение может проверить наличие этой записи, если правило отражено в его настройках.

| Что видит студент | Что происходит с информацией | Что можно проверить |
| --- | --- | --- |
| Поля «Кабинет» и «Описание» | Получение данных | Поля различимы, кабинет можно указать |
| Сообщение «Укажите кабинет» | **Проверка**{:.action} ввода | После ошибки нет номера новой заявки |
| «Заявка № 101 принята» | Карточка сохранена, номер показан | Заявку можно найти по номеру |
| Статус «В работе» | **Результат**{:.result} обновления представлен пользователю | Изменение видно после принятия заявки |

Представь, что в другой организации для той же задачи пока используют общую таблицу. Форму ввода и интерфейс можно заменить, сохранив принцип: зафиксировать событие, назначить ответственного, показать итог. Так легче понять различие между технологией и отдельным инструментом. Инструмент помогает выполнить шаг, а технология связывает шаги с целью.

### Как выбирать уровень в пограничных случаях

Классифицируй объект по тому, **какую роль он играет в описании**. При слове «Интернет» говорим об инфраструктуре обмена, поэтому выбираем **глобальный уровень**{:.global}. При словах «веб-обмен» описываем общий способ взаимодействия, который одинаково применим в разных областях, поэтому выбираем **базовый уровень**{:.base}. При словах «приём заявок в колледже» есть конкретная задача, роли и результат. Это **конкретный уровень**{:.concrete}.

Рассмотрим электронную очередь в поликлинике. Связь между устройствами обеспечивает сеть. Браузер показывает расписание и обменивается данными с приложением с помощью веб-технологий. Сама электронная запись подбирает врача, дату и свободное время. В отчёте запиши эти три объекта отдельными строками. Если записать одним словом «сайт», будет трудно определить, говоришь ли ты о способе обмена или о прикладном сервисе.

Один и тот же сервис можно классифицировать ещё по назначению. Электронный дневник решает учебную задачу. Электронный документооборот помогает управлению. Мониторинг оборудования относится к производству. Во всех трёх случаях могут применяться одинаковые **базовые технологии**{:.base} хранения и передачи. Сравнение по двум признакам даёт полное описание: «электронный дневник — конкретная технология по уровню, образовательная по назначению».

### Разбор записи для отчёта ПР01

**Шаг 1. Запиши наблюдение.** «На вкладке Network при открытии страницы виден запрос к HTML-документу». Если в работе был найден JSON, назови одно открытое поле без личных данных. Указывай фактически наблюдавшийся ресурс: обычная статическая страница может вообще не обращаться к JSON.

**Шаг 2. Назови технологию.** Запрос и ответ относятся к **веб-обмену**{:.base}. Добавь обоснование: «Тот же способ используется в разных сервисах». Если обсуждаешь функцию «выдать пользователю список его заявок», это уже прикладная цель сервиса.

**Шаг 3. Отметь границу вывода.** Ответ показывает содержимое, доступное браузеру. Название серверной СУБД можно подтвердить документацией проекта или другим независимым свидетельством. В отчёте полезно написать, что именно видишь в Response и какой вывод из этого следует.

Попробуй заполнить карточку без компьютера. **Условие:** браузер получил HTML страницы расписания, на экране студент видит пары на завтра. Назови уровень веб-обмена и уровень показа расписания. **Контроль:** веб-обмен — базовый способ, показ расписания конкретной группы — прикладная технология. В двух предложениях объясни, где применишь ту же схему классификации, например при разборе электронного журнала или интернет-магазина.

### Самопроверка

1. Какой компонент задаёт, кто закрывает заявку?
2. Какой уровень у Интернета, веб-обмена и сервиса заявок?
3. Может ли сервис относиться сразу к образовательным и конкретным технологиям?

<details markdown="1">
<summary>Ответы</summary>

1. Организационная процедура, которую приложение может закрепить правами доступа.
2. Соответственно **глобальный**{:.global}, **базовый**{:.base} и **конкретный**{:.concrete}.
3. Да. Первое слово описывает область применения, второе — уровень классификации.

</details>

**Под запись.** Информационная технология объединяет средства и процедуры. В отчёте уровень технологии обосновывают по её роли и отдельно указывают, что было видно в интерфейсе или инструменте наблюдения.

## 02. Информационные технологии в промышленности

**Цель пары.** Проследить путь от измерения до действия и объяснить, зачем производству заданный интервал измерений, порог и журнал событий.

### От физического события к записи

В производственном помещении нужно заметить, что оборудование перегревается. **Датчик**{:.source} измеряет температуру. В учебной модели контроллер получает измерение раз в минуту и **сравнивает его с порогом**{:.action}. Если температура не ниже 70 °C, он создаёт **предупреждение**{:.result}. Оператор видит, какое оборудование проверять. Журнал позволяет позже посмотреть время события и реакцию человека. Значение 70 °C условное и служит только для разбора алгоритма.

Измерение удобно хранить как запись «время, идентификатор устройства, значение, единица». Если оставить только число 71, по нему нельзя определить, какой датчик сработал, когда и в каких единицах сделано измерение. Если разные узлы записывают время по разным часам, события сложнее сопоставлять.

### Разбор правила на контрольных данных

| Время | Датчик | Температура | Правило ≥ 70 °C |
| --- | --- | ---: | --- |
| 10:00 | D1 | 66 °C | В норме |
| 10:01 | D1 | 70 °C | Предупреждение |
| 10:02 | D1 | 69 °C | В норме по этому правилу |
| 10:03 | D1 | 72 °C | Предупреждение |

При замене условия «не ниже 70» на «выше 70» строка 10:01 изменит результат. Поэтому граница должна быть записана в требованиях и проверена отдельным тестом. Если система создаёт новое уведомление на каждое измерение выше порога, одно длительное событие может породить несколько одинаковых предупреждений. Для оператора полезнее видеть, когда событие началось, продолжается и завершилось. Для этого хранят состояние предупреждения.

### Как выбрать технологию

Для разового наблюдения можно записать значения в таблицу. Для круглосуточного контроля нужны автоматический сбор, передача и своевременное уведомление. Передача данных относится к **базовому способу работы**{:.base}, а мониторинг конкретного станка — к **прикладной технологии**{:.concrete}. При проектировании уточняют допустимую задержку, ответственного и действия при пропуске измерений.

### Как читать пропуски и повторы в журнале

Производственная система должна отдельно учитывать измерение и событие. Показание 72 °C — измерение. Запись «началось превышение» — событие перехода. Если значения 72, 73 и 72 приходят подряд, оператору нужна одна активная запись с временем начала и последним показанием. При возвращении к норме журнал отмечает окончание события. Позже по двум отметкам можно рассчитать его длительность.

Пропуск измерения выделяют отдельным состоянием. Например, в 10:04 датчик не передал значения. Логика показывает «нет данных за 10:04», оператор проверяет связь с устройством. Нулевое значение имело бы другой смысл и могло бы скрыть неполадки передачи. У каждого входа должны быть время, идентификатор источника и единица измерения. Если два датчика обозначены одинаково, данные нельзя уверенно связать с конкретным устройством.

### Разбор на доске: когда создать предупреждение

Представь, что по учебному правилу событие начинается только после **двух последовательных измерений**{:.action} не ниже 70 °C. Пропуск обнуляет счётчик подтверждений. На каждом шаге выписывай время, значение и счётчик.

| Время | Значение | Счётчик после шага | Ожидаемый выход |
| --- | --- | ---: | --- |
| 10:00 | 69 °C | 0 | В норме |
| 10:01 | 70 °C | 1 | Ожидаем следующее измерение |
| 10:02 | Нет данных | 0 | Сигнал о пропуске данных |
| 10:03 | 71 °C | 1 | Ожидаем подтверждение |
| 10:04 | 72 °C | 2 | **Предупреждение**{:.result} |

Сравни этот вариант с правилом из начала лекции. Простое сравнение реагирует в 10:01, требование двух измерений впервые реагирует в 10:04. Второй вариант снижает реакцию на единичные скачки, но добавляет ожидание. Перед внедрением инженер должен выбрать допустимую задержку для оборудования. Здесь мы сравниваем правила на вымышленном наборе, как это делают при проверке алгоритма.

**В отчёте.** Достаточно указать правило, привести одну пограничную строку и пояснить, что изменится при другом условии. Такой разбор встречается при мониторинге температуры, количества изделий и доступности устройств.

### Самопроверка

1. Сработает ли строгое условие «больше 70» на значении 70?
2. Что означает отсутствие строки от датчика за минуту?
3. Что добавить, чтобы различать первый сигнал и продолжение события?

<details markdown="1">
<summary>Ответы</summary>

1. Нет. Для срабатывания при 70 требуется условие «больше или равно».
2. Измерение за этот интервал недоступно. По этому признаку нельзя объявить, что температура в норме.
3. Идентификатор события, время начала и текущее состояние.

</details>

**Под запись.** Производственная ИТ связывает измерение, правило, сигнал и действие. Для проверки алгоритма нужны значения по обе стороны порога и на границе.

## 03. Информационные технологии в управлении

**Цель пары.** Описать маршрут заявки, выделить роли и понять, зачем хранить переходы между статусами.

### Маршрут вместо общей папки

Обращение прошло три этапа: студент его отправил, лаборант назначил исполнителя, исполнитель закрыл работу. Если каждому участнику просто отправить копию документа, со временем появятся разные версии. **Маршрут согласования**{:.action} определяет, кто и в каком порядке работает с одним объектом. Электронный документооборот применяет этот подход к заявлениям, договорам и служебным запискам. У заявки на ремонт похожая логика, хотя этапов меньше.

У процесса есть **роль**, **состояние** и **действие**. Роль описывает ответственность. Состояние отвечает на вопрос «что с заявкой сейчас?». Действие изменяет состояние при выполнении условия. Например, лаборант принимает новую заявку, но для закрытия исполнитель должен заполнить поле «Что сделано». В учебной модели решение «закрыть» нельзя выполнить из состояния «Новая». Это ограничение проверяется на уровне приложения.

### Разбор карточки № 101

| Событие | Роль | Время | Состояние после действия |
| --- | --- | --- | --- |
| Отправить карточку | Студент | 09:20 | Новая |
| Взять в работу | Лаборант | 10:00 | В работе |
| Записать результат | Исполнитель | 11:30 | Закрыта |

По карточке можно узнать текущее состояние, а по **журналу событий**{:.source} — путь. Время ожидания начала работы равно 40 минутам. Полное время от создания до закрытия — 130 минут. Если хранить только статус «Закрыта», ни один из этих интервалов уже не восстановить. В реальном процессе надо договориться, с какого события считать срок, иначе разные отчёты покажут разные числа.

### Где применяется

Реестр подходит для быстрой сводки. Система маршрутизации пригодится, когда у объекта несколько владельцев по очереди, нужны сроки и правила доступа. В расписании производства согласуют изменение заказа, в колледже обрабатывают заявление, в сервисе заявок назначают ремонт. Общий подход переиспользуется, предметные поля и ответственные меняются.

### Какие правила записать до разработки

Возьми состояние «Новая». У лаборанта есть команда «Взять в работу». У студента есть просмотр статуса. После принятия заявки появляется назначенный исполнитель. При закрытии исполнитель указывает результат ремонта. Удобно свести правила в матрицу: «состояние → роль → действие → обязательное поле → следующий статус». Так можно заранее увидеть, что происходит с заявкой после каждого действия и где нужна проверка.

В рабочем процессе возможен возврат. Допустим, исполнитель отметил «Выполнена», но оборудование снова отказало. Есть как минимум два обоснованных сценария: открыть новую связанную заявку либо вернуть старую в работу, записав причину. Выбор меняет статистику: в первом случае вырастет число обращений, во втором — длительность жизненного цикла исходной карточки. Правило важно согласовать до расчёта отчётов, чтобы участники одинаково понимали показатель.

Если два сотрудника одновременно открыли новую заявку, система должна показать, кто успел её принять. В интерфейсе можно дать обратную связь «Заявка уже в работе» и предложить обновить список. В журнале понадобится информация о переходе и об исполнителе. Так администратор сможет восстановить ход событий даже при задержке на одном из экранов.

### Проверь карточку по двум попыткам

1. Исходное состояние «Новая». Студент выбирает команду закрытия. **Контроль:** заявка сохраняет состояние, действие для этой роли недоступно либо отклоняется приложением.
2. Лаборант принимает ту же карточку в 10:00. **Контроль:** появляется запись о переходе «Новая → В работе», видно ответственного.
3. Исполнитель пытается закрыть её с пустым результатом. **Контроль:** система сообщает, какое поле заполнить, статус остаётся «В работе».
4. Исполнитель заполняет результат и подтверждает действие. **Контроль:** новая запись в журнале, статус «Закрыта».

Такой набор проверяют при внедрении документооборота, поддержки пользователей или согласования закупок. В мини-отчёте выбери один разрешённый и один отклонённый переход, затем опиши, какое правило определило результат.

2. Исполнитель после заполнения результата.

## 04. Информационные технологии в обучении

**Цель пары.** Понять, какие учебные задачи решают электронный учебник, система управления обучением и средства совместной работы.

### От чтения материала к обратной связи

Студенту нужно открыть лекцию, выполнить работу и получить замечания. Эти задачи могут быть распределены между несколькими сервисами. Электронный учебник публикует материалы. Система управления обучением (LMS) может принимать задания, фиксировать срок сдачи и показывать персональную обратную связь. Совместный редактор помогает группе работать над одним документом. Задача определяет, какой инструмент уместен на каждом шаге.

Этот сайт раздаёт **учебные страницы**{:.concrete} по общей ссылке. Для доступа к тексту лекции достаточно браузера. Чтобы преподаватель мог принять работу от конкретного студента, ему нужен отдельный канал сдачи и способ связать работу с автором. Само открытие страницы ещё ничего не говорит о понимании темы. Понимание проверяют по результату действия и объяснению.

### Сценарий для ПР01

Преподаватель выдаёт ссылку на задание. Студент выполняет наблюдение в DevTools, сохраняет собственный отчёт и сдаёт его через принятый в группе канал. Преподаватель проверяет, можно ли повторить шаги и следует ли классификация из наблюдения. Если в ответе написано «увидел серверную базу», а на скриншоте только JSON, обратная связь должна указать, какое утверждение подтверждается и какого свидетельства не хватает.

| Что нужно группе | Подходящий инструмент | Что считаем результатом |
| --- | --- | --- |
| Читать одинаковый материал | Электронный учебник | Страница доступна и имеет постоянную ссылку |
| Сдавать индивидуальный отчёт | LMS или утверждённый канал сдачи | Есть автор, файл и дата |
| Согласовать шаблон отчёта | Совместный документ | Понятно, что входит в итоговую версию |
| Разобраться с трудным понятием | Тренажёр или демонстрация | Студент объясняет результат своими словами |

### Доступ и проверка

Публичная ссылка полезна для теории, которой можно делиться. Индивидуальные оценки и работы доступны участникам процесса в соответствии с их ролями. Для отчёта можно подготовить учебный набор без персональных данных, чтобы вся группа могла повторить действия.

### Что именно показывает прогресс

Представь две ситуации. Первый студент пять раз открыл страницу и один раз выполнил задание. Второй открыл её один раз, сразу воспроизвёл шаги и объяснил итог. Счётчик открытий характеризует использование сайта. Качество работы лучше оценивать по выполненному заданию, объяснению и контрольному результату. Поэтому в учебной системе полезно разделять события «открыта лекция», «отправлена работа» и «работа проверена». У каждого события своё назначение.

Обратная связь должна помогать исправить конкретный шаг. В отчёте по ПР01 студент утверждает, что `200` означает применение базы данных. В замечании можно написать: «Код ответа свидетельствует об успешном запросе. Добавь колонку “наблюдение” и обоснуй базовый уровень веб-обмена». После исправления преподаватель проверяет именно исправленную строку. Так технология поддерживает учебную задачу, а не сводится к обмену файлами.

### Проектируем маршрут сдачи

Условия: у группы общая лекция, единый шаблон отчёта и индивидуальные результаты. Составь маршрут из четырёх шагов. На каждом шаге назови исполнителя и **контрольный результат**{:.result}.

| Шаг | Исполнитель | Как проверить |
| --- | --- | --- |
| Опубликовать теорию | Преподаватель | Ссылка открывает нужную тему |
| Выполнить наблюдение | Студент | В отчёте есть конкретный пример |
| Передать работу на проверку | Студент | Видны работа, автор и дата сдачи |
| Дать обратную связь | Преподаватель | Автор видит замечание и понимает, что исправить |

Подумай, какие данные нужны всей группе, а какие — только преподавателю и автору. Для всех можно опубликовать шаблон и учебный пример. Для индивидуального отчёта нужен согласованный способ сдачи. Если в отчёте используются скриншоты, достаточно фрагмента, который подтверждает наблюдение и не раскрывает личных сведений.

**Применение.** Та же схема встречается в обучении сотрудников: общий инструктаж, личное прохождение задания, проверка и обратная связь. Итог формулируют через наблюдаемое действие сотрудника.

## 05. Модели информационных технологий

**Цель пары.** На одном примере различить модель данных, модель процесса и модель ролей.

### Что сохраняет модель

**Модель** — описание объекта или процесса, которое оставляет сведения, важные для вопроса. Модель пути заявки не обязана показывать каждый байт запроса. Схема данных не обязана показывать, куда нажимает пользователь. Выбор модели зависит от того, что мы хотим проверить.

Для вопроса «какие поля нужны в карточке?» подойдёт модель данных: идентификатор, кабинет, описание, состояние, дата создания. Для вопроса «что должно происходить при отправке?» нужна модель процесса: ввести → проверить → сохранить → показать номер. Для вопроса «кто может изменить статус?» нужна модель ролей: студент создаёт, лаборант принимает, исполнитель закрывает. Эти модели должны согласовываться: если модель процесса требует кабинет, модель данных должна его хранить.

### Построй процесс с развилкой

1. Пользователь вводит кабинет и описание.
2. **Проверка**{:.action} определяет, заполнены ли обязательные поля.
3. При корректном вводе приложение сохраняет карточку и показывает **номер заявки**{:.result}.
4. При пустом кабинете приложение показывает сообщение о поле и предлагает исправить ввод.

На доске можно отметить шаги прямоугольниками, условие — ромбом, варианты — стрелками «да» и «нет». Подпиши у каждого выхода ожидаемый результат. Ветка ошибки должна объяснять, как пользователь возвращается к вводу. Если стрелка ошибки ведёт сразу к сохранению, схема расходится с правилом.

### Проверка двух сценариев

| Вход | Ожидаемое поведение | Что наблюдаем |
| --- | --- | --- |
| Кабинет 302, «Монитор не включается» | Сохраняется карточка | Видно номер заявки |
| Кабинет пустой, то же описание | Сохранение отклонено | Видно сообщение о кабинете |

Модель пригодится разработчику, который реализует проверку, и тестировщику, который составляет сценарии. Её можно сначала нарисовать в тетради, затем перевести в схему отчёта.

### Как сверить три модели между собой

Представим три записи в требованиях. В модели данных поля «кабинет» и «описание» обязательны. В модели процесса после отправки формы стоит условие «оба поля заполнены?». В модели ролей студент может создать карточку, а лаборант может принять её. Для каждого сценария проверь, что все три модели отвечают согласованно. Например, студент может отправить заполненную форму, а роль лаборанта понадобится только после создания.

Если в схеме указано обязательное поле «кабинет», а в модели данных его нет, два исполнителя сделают разные выводы. Разработчик базы не создаст нужное поле, а разработчик формы добавит проверку. Подобные противоречия дешевле заметить до программирования. Для этого удобно оформить таблицу «требование → модель → проверяемый результат» и пройти по ней вместе.

### Самостоятельный разбор развилки

Добавь к модели поле «Номер компьютера». Оно обязательно только при обращении об оборудовании. Для заявки о проблеме с сетью достаточно кабинета и описания.

1. В модели данных запиши тип обращения и поле номера. Обозначь условие обязательности.
2. На схеме после проверки кабинета поставь вопрос «Тип — оборудование?». При ответе «да» проверь номер компьютера. При ответе «нет» переходи к сохранению.
3. Подбери входы: «оборудование, 302, ПК-06», «оборудование, 302, пусто», «сеть, 302, пусто».
4. **Контрольные выходы**{:.result}: первый вход сохраняется, второй получает сообщение о номере, третий сохраняется при заполненном описании.

Сравни схемы двух студентов. Обе годятся, если приводят к одинаковым выходам и на каждой стрелке ясно, почему выбран этот путь. В отчёте пригодится схема и одна строка, где проверяется исключение. Такие модели используют при проектировании форм, обработке заказов и проверке заявок в управлении.

### Самопроверка

1. Какую модель открыть, чтобы найти обязательные поля?
2. Где искать правила перехода при ошибке?
3. Какое требование выявится, если повторное нажатие может создать две карточки?

<details markdown="1">
<summary>Ответы</summary>

1. Модель данных и правила заполнения.
2. В модели процесса.
3. Нужна обработка повторной отправки. Ожидаемое число созданных записей надо указать явно.

</details>

**Под запись.** Модель зависит от вопроса. Сценарий описывают через вход, действие, развилку и проверяемый выход.

## 06. Методы и средства реализации

**Цель пары.** Отличать общий метод решения, последовательность действий и инструмент, которым она выполняется.

### Один метод, разные реализации

Лаборанту надо узнать, сколько открытых заявок приходится на каждый кабинет. **Метод** состоит в том, чтобы **отобрать нужные записи, сгруппировать и подсчитать**{:.action}. **Алгоритм** уточняет порядок: взять очередную запись, проверить статус, прибавить единицу счётчику её кабинета, повторять до конца списка. **Средство** выполняет выбранные действия: например, Excel со сводной таблицей или СУБД с запросом.

Метод остаётся понятным даже при смене инструмента. Это помогает проверить результат двумя способами. Если вручную и в программе получились разные цифры, нужно посмотреть, одинаковы ли входные данные, фильтр и определение показателя.

### Воспроизводимый расчёт

| Заявка | Кабинет | Статус |
| --- | --- | --- |
| 101 | 302 | Открыта |
| 102 | 302 | Закрыта |
| 103 | 303 | Открыта |
| 104 | 302 | Открыта |

Сначала зачеркни строку 102. На листе рядом с «302» поставь две отметки, рядом с «303» — одну. **Контрольный результат**{:.result}: кабинет 302 — 2, кабинет 303 — 1, всего — 3. Проверка: сумма двух групп равна числу строк, оставшихся после фильтра.

Условие «открытые» здесь соответствует одному значению в поле статуса. В реальной системе статус «В работе» тоже может считаться активным. Перед расчётом закрепи определение. Слово «активная» без перечня состояний создаёт расхождение между отчётами.

### Как объяснять выбор средства

Для четырёх строк ручной расчёт удобен как эталон. Для списка на сотни строк таблица помогает быстро получить сводку. Для повторяющегося отбора из связанных данных подойдёт запрос. В отчёте укажи, какие действия выполнял инструмент и какой контрольный расчёт подтвердил результат.

### Почему два расчёта могут расходиться

Представь, что Excel показывает три открытые заявки, а запрос к базе — четыре активные. Сначала проверь значение каждого показателя. Для одного отчёта открыты только карточки со статусом «Открыта». Для другого активны «Открыта» и «В работе». Обе цифры могут быть верными при своих определениях. Если нужен единый результат, согласуй условие отбора, источник и момент выгрузки.

Затем проверь способ реализации. При обновлении файла новая строка может оказаться за пределами диапазона. Запрос может использовать другую дату или учитывать дополнительные кабинеты. Удобно начинать с нескольких строк, которые легко обработать вручную. Когда маленький набор даёт одинаковый результат, повторяй проверку на полном наборе и сравнивай промежуточные итоги.

### Разбор: добавить новое состояние

К исходным строкам добавь заявку 105 из кабинета 303 со статусом «В работе» и заявку 106 из кабинета 304 со статусом «Закрыта». Сформулируй две задачи. Для первой считаем только открытые. Для второй считаем активные, то есть открытые и взятые в работу.

1. Выпиши допустимые значения статуса для каждого показателя.
2. Отметь номера оставшихся заявок.
3. Сгруппируй номера по кабинетам.
4. Сверь суммы групп с числом отмеченных записей.

**Контрольные результаты**{:.result}: открытые — 101, 103, 104, всего 3. Активные — 101, 103, 104, 105, всего 4. По кабинетам активных заявок: 302 — 2, 303 — 2. Строка 106 исключается из обеих выборок.

Алгоритм можно передать одногруппнику как последовательность команд, блок-схему или точное описание. В отчёте добавь исходное правило, выбранный инструмент и проверку. В работе с обращениями, продажами и журналами измерений такой контроль помогает объяснять цифры другим людям.

### Самопроверка

1. Что из примера является методом?
2. Как изменится итог, если строка 102 станет открытой?
3. Чем «сделал в Excel» отличается от описания алгоритма?

<details markdown="1">
<summary>Ответы</summary>

1. Отбор, группировка и подсчёт.
2. Кабинет 302 — 3, кабинет 303 — 1, всего — 4.
3. Название программы указывает средство. Алгоритм перечисляет действия и условия.

</details>

**Под запись.** Метод объясняет способ решения, алгоритм задаёт шаги, средство реализует их. Проверяемый итог помогает сравнивать реализации.

## 07. Веб-технологии и обмен по API

**Цель пары.** Объяснить путь запроса от браузера до ответа и связать виды ресурсов с наблюдениями ПР01.

### Как страница получает данные

Браузер действует как клиент. Он отправляет **HTTP-запрос**{:.base}, а сервер возвращает ответ. Страница может сначала получить HTML, CSS и JavaScript. HTML задаёт структуру, CSS — оформление, JavaScript может реагировать на действия и запрашивать данные. Один экран может быть собран из нескольких ответов. Поэтому число запросов зависит от страницы, кэша, открытых разделов и действий пользователя. [Обзор HTTP, MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

**API**{:.base} задаёт правила взаимодействия программ: какие адреса и параметры допустимы, как выглядит результат, как сообщаются ошибки. JSON — один из способов представить данные. Например, учебный ответ может содержать объект `{"id":101,"room":"302","status":"open"}`. В нём три поля. Пользователь видит карточку, а программа работает со значениями полей.

### Один запрос, три результата

| Что произошло | Пример ответа | Что показать пользователю |
| --- | --- | --- |
| Есть открытые заявки | Успех и массив записей | Список заявок |
| Подходящих заявок нет | Успех и пустой массив `[]` | «Открытых заявок нет» |
| Сервер не обработал запрос | Ошибка сервера | Сообщение о сбое и возможность повторить |

Открытый список и его пустой результат отличаются по содержимому. Сбой отличается по самому факту выполнения запроса. Если в интерфейсе все три состояния выглядят как пустое окно, пользователю трудно понять, ждать или обратиться за помощью.

### Где это видно в ПР01

Открой уже сделанный отчёт и выбери один публичный запрос на чтение. Запиши тип ресурса, код ответа и два поля, если ответ содержит открытые данные. Из таблицы Network видно, что браузер получил. Внутреннее устройство сервера по этой таблице устанавливают только при наличии дополнительной документации.

### Из чего состоят запрос и ответ

У запроса есть метод и адрес ресурса. У ответа есть код состояния, заголовки и, когда это предусмотрено, содержимое. Заголовок типа содержимого помогает программе понять, пришёл ли HTML, JSON или другой формат. В учебном интерфейсе адрес «список заявок со статусом open» выражает задачу, код `200` подтверждает успех, а массив содержит найденные элементы. Отсутствие элементов и сетевой сбой дают разные сигналы. [Коды состояния HTTP, MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)

Допустим, два клиента используют один договор API: браузер и приложение лаборанта. Браузер рисует таблицу, приложение — список карточек. Они могут по-разному оформлять идентификатор 101, но оба должны прочитать поле одинаково. Если разработчик изменит имя поля `room` на `classroom`, потребителям понадобится согласованное обновление. Поэтому состав полей описывают заранее, а формат проверяют примерами.

## 08. Сетевой доступ, облако и совместная работа

**Цель пары.** Сопоставить локальную папку, сетевой ресурс и облачный сервис по задачам доступа, совместного редактирования и восстановления.

### Где живёт рабочая копия

В локальной папке файл доступен на одном компьютере. В общей сетевой папке участники могут открыть файлы с разных устройств, если есть доступ к сети. В приложении с совместным редактированием пользователи могут работать с одним документом, а приложение ведёт историю и регулирует доступ. Облачный сервис использует удалённую инфраструктуру, где могут предоставляться вычисления, хранение и готовые приложения.

Общий доступ отвечает на вопрос «кто сейчас может прочитать или изменить данные?». **Резервное копирование**{:.action} отвечает на вопрос «из чего можно восстановить рабочее состояние после сбоя?». История правок помогает увидеть изменения в документе. Проверка резервной копии требует восстановить её в отдельном месте и убедиться, что нужные данные читаются.

### Разберём колледж

Два лаборанта хотят вести реестр на разных компьютерах. При обмене копиями по почте возникает вопрос, чей реестр актуален. При общей папке остаётся вопрос, как редактировать файл одновременно. В веб-сервисе оба смотрят на текущие данные через браузер. Когда один принимает заявку, другому следует увидеть новое состояние до того, как он начнёт ту же работу. Приложение должно согласовать действия и сообщить об изменении.

Определи права на примере. Студент видит и создаёт свои заявки. Лаборант читает назначенные ему карточки и обновляет их. Администратор управляет ролями. Разграничение доступа помогает сохранить ответственность и ограничить ненужное раскрытие сведений.

### Проверка сценариев

| Ситуация | Что проверяем |
| --- | --- |
| Пропала сеть | Как узнать, что отправка не подтверждена |
| Два человека открыли карточку | Как оба узнают, что заявка уже принята |
| Утерян рабочий файл | Читается ли резервная копия и какой у неё момент сохранения |

### Разница между общей версией и копией

Представь, что два лаборанта получили одинаковый файл. Первый поменял статус заявки 101, второй обновил 103. Теперь нужно объединить правки. Если оба пересылают целый файл, одна версия может затереть другую. При общей записи интерфейс читает согласованное состояние с сервера. История изменений помогает установить, кто и когда поменял конкретную карточку.

Резервная копия отвечает за восстановление после потери. Допустим, вчера в 18:00 сохранили копию, а сегодня в 09:20 появился новый номер 108. Если рабочее состояние утрачено, копия за вчера вернёт карточки, которые были в ней к 18:00. Для восстановления более поздней записи понадобится более свежая копия или другой источник событий. Поэтому при проверке указывают момент создания копии и допустимый объём потери данных.

### Два задания на выбор способа работы

**Сценарий А.** Один преподаватель готовит исходный документ, студенты читают опубликованную версию. Контроль: студент открывает последнюю опубликованную версию, а редактировать исходник может ответственный. Возможная реализация — рабочий файл преподавателя и отдельная страница для чтения.

**Сценарий Б.** Три сотрудника параллельно ведут заявки из разных кабинетов. Контроль: у каждой записи есть одно текущее состояние, видны изменения и действует ограничение по ролям. Возможная реализация — общее приложение с хранением записей и правилами обновления.

Сравни сценарии по доступу, совместному редактированию и восстановлению. Запиши, что изменится при отключении сети. Для отчёта выбери один сбой и напиши цепочку «признак → где проверить → что считается успешным восстановлением». Например, карточка снова открывается по номеру, а связанная история содержит те же события до времени копии.

### Самопроверка

1. Сколько актуальных версий должно быть у общей записи?
2. Почему доступ к общей папке сам по себе не подтверждает возможность восстановления?
3. Кто должен иметь право назначать роли?

<details markdown="1">
<summary>Ответы</summary>

1. Одна согласованная версия. У разных участников интерфейс может обновляться с задержкой.
2. Общий доступ позволяет работать с текущими файлами. Нужна пригодная резервная копия и проверка восстановления.

## 09. Автоматизация, аналитика и машинное обучение

**Цель пары.** Различать действие по заданному правилу, сводку по накопленным данным и предложение модели по новому примеру.

### Три вопроса к одному сервису

«Есть ли занятие в кабинете сейчас?» — вопрос для **автоматического правила**{:.action}. Если занятие идёт и оборудование мешает его проведению, система может предложить высокий приоритет. «Какие типы неисправностей повторяются чаще?» — задача **аналитической обработки**{:.action}. Она требует накопленных записей и определённого периода. «Какую категорию предложить по новому тексту?» — задача модели классификации, которую можно обучить на примерах.

Правило с явным условием легко проверить на границе. Статистическая модель использует закономерности из данных и может ошибаться на новых формулировках. В обоих случаях нужен способ проверить выход. Если от категории зависит срочный ремонт, человеку следует видеть основание решения и иметь возможность исправить предложение.

### Мини-разбор набора

Из этих чисел нельзя сделать вывод, что следующая заявка обязательно будет про сеть. Для новой строки «Компьютер не включается после отключения света» модель может предложить категорию «Электропитание». Лаборант проверит, есть ли такая категория в принятом справочнике.

Для сравнения ручного правила и модели подготовь несколько новых сообщений с проверенными метками. По каждому зафиксируй вход, предложенную категорию и решение человека. Если модель верно обработала 7 из 10 примеров, на этом наборе доля совпадений составляет 70%. Для выводов о работе на всём потоке нужна выборка, похожая на реальные заявки, и отдельный разбор ошибок.

### Как выбрать способ автоматизации

Сначала уточни цену ошибки. Если открытие заявки зависит от того, заполнен ли кабинет, подходит явная **проверка**{:.action}: кабинет указан и есть в справочнике. Правило можно повторить для каждого входа. Когда в архиве сотни записей, **аналитическая сводка**{:.result} помогает найти повторяющиеся категории. Если формулировки новых заявок сильно различаются, модель может предложить категорию по тексту. Человек сверяет её с реальной причиной неисправности.

Задача модели формулируется заранее. В нашем примере на входе текст, на выходе одна из категорий: «Сеть», «Оборудование» или «ПО». Для проверки нужны заявки с согласованными правильными категориями. Если один сотрудник относит «не открывается сетевой диск» к ПО, а другой к сети, сначала следует уточнить правила разметки. Оценка будет зависеть от того, насколько последовательно подготовлены примеры.

Запись «302» сама по себе неоднозначна. Поле «кабинет» задаёт контекст, в котором значение становится полезным. **Исходные данные**{:.source} могут появиться при вводе, измерении или чтении файла. ### Часть А. Сравни решения на конкретных условиях

Преподаватель ведёт 12 записей один, итог нужен раз в неделю. Для этого подойдёт **электронная таблица**{:.base} с полями «кабинет», «статус», «дата» и сводкой. Подготовь два требования в форме «условие → действие → наблюдаемый выход». Пример: «Кабинет выбран из справочника, описание заполнено → отправить → показать номер». Для проверки пустого кабинета ожидается подсказка и отсутствие новой карточки. Чем точнее критерий, тем проще сравнить варианты реализации. Слова «быстро» или «удобно» уточняют до условий проверки, например «лаборант находит заявку по её номеру из списка».

### Часть Б. Найди точку проверки при сбое

Студент ввёл кабинет 302, увидел «отправляем» и закрыл страницу до подтверждения. Действия в браузере показывают состояние интерфейса, а **результат хранения**{:.result} проверяется по карточке или по подтверждённому номеру. Если ответ потерялся, запись могла остаться на сервере. Чтобы разобрать ситуацию, перечисли этапы по порядку: ввод → передача → проверка → сохранение → ответ → показ. Затем для каждого этапа укажи доступный признак.

1. При вводе видны заполненные поля.
2. При проверке некорректного входа видно конкретное сообщение.
3. После сохранения карточку можно открыть по идентификатору.
4. После представления карточки лаборант может выбрать следующее действие.

**Контроль для отчёта.** Выбери случай «пустой кабинет». Укажи, где обнаружена ошибка, что увидит студент и какой записи в реестре ожидаешь. Вариант ответа: проверка отклоняет вход, интерфейс просит выбрать кабинет, новая запись отсутствует. Это связывает требования из темы 1 с процессами темы 2.
