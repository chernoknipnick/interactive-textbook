# Основы ООП — собираем всё вместе

## 1. Что теперь должно сложиться в одну картину

До этой темы мы рассматривали отдельные части: **класс**, **объект**, **ссылку**, **поле**, **метод**, **конструктор** и `static`. Теперь нужно увидеть, как они работают вместе и зачем вообще организовывать программу через объекты.

**Объектно-ориентированное программирование**, или **ООП**, — подход, при котором решение организуют через объекты с состоянием и доступными действиями. Например, у конкретного телефона есть заряд, а его действие `use()` расходует этот заряд. У второго телефона своё состояние: использование первого само по себе не разряжает второй.

Главный вопрос при чтении такой программы: **какой именно объект сейчас получает действие и какие данные меняются?** Одного знания слова `class` для ответа недостаточно: нужно следить за ссылками и вызовами.

Эта лекция завершает начальный блок и даёт карту следующих тем. Инкапсуляцию мы уже применяли; наследование, абстракцию и полиморфизм сначала рассмотрим на понятной модели. Их подробные правила и более сложные случаи можно изучать дальше по отдельности.

## 2. Словарь: у каждого понятия своя работа

| Понятие | Простое объяснение | Пример |
|---|---|---|
| **Класс** | Описание устройства экземпляров и доступных действий | `Phone` |
| **Объект**, или **экземпляр** | Конкретный созданный экземпляр класса | Телефон Анны с зарядом 80 |
| **Поле** | Переменная, объявленная в классе; может относиться к экземпляру или классу | Личный `battery`, общий `createdCount` |
| **Метод** | Объявленное действие или вычисление | `use()`, `getBattery()` |
| **Конструктор** | Часть инициализации нового экземпляра | `Phone("Анна", 80)` после `new` |
| **Ссылка** | Значение, через которое можно обратиться к объекту | Значение переменной `anna` |
| **Параметр** | Переменная, принимающая значение при вызове | `int battery` в конструкторе |
| **Аргумент** | Конкретное значение или выражение в вызове | `80` в `new Phone("Анна", 80)` |
| **Инкапсуляция** | Организация доступа к состоянию через предусмотренные действия и правила | Закрытый заряд и метод его расходования |

Телефон из магазина — аналогия. Программный объект не обязан изображать физическую вещь: объектами могут быть заказ, сообщение, игровой ход или результат проверки.

## 3. Общая форма: где описание, а где использование

Это шаблон, а не готовая программа. Слова с русскими именами нужно заменить реальными объявлениями и выражениями:

```text
class ИмяКласса {
    private Тип имяПоля;

    ИмяКласса(Тип имяПараметра) {
        this.имяПоля = имяПараметра;
    }

    public void имяДействия() {
        инструкции;
    }
}

ИмяКласса имяПеременной = new ИмяКласса(аргумент);
имяПеременной.имяДействия();
```

Имя собственного класса, поля, параметра, переменной и метода выбирает программист. После выбора имена в объявлениях и обращениях должны быть согласованы. Можно назвать действие `use`, `sendMessage` или иначе, если это подходящее допустимое имя и объявлен соответствующий метод.

Но `class`, `private`, `public`, `void`, `this` и `new` — слова языка. Их нельзя заменить любимыми словами. Имя конструктора обязано совпадать с именем класса. Имя готового библиотечного метода, например `println`, также нельзя произвольно менять в вызове.

Последние две строки шаблона — инструкции использования. В наших обычных примерах они находятся внутри `main`, а не свободно между объявлениями классов.

## 4. Первый опыт целиком: два телефона и три ссылки

Сохрани следующий самостоятельный пример в **OopSummaryDemo.java**. Здесь один публичный класс запуска и отдельный непубличный класс `Phone`. Это один исходный файл. Классы с одинаковыми именами из других лекций в эту папку добавлять не нужно.

```java
public class OopSummaryDemo {
    public static void main(String[] args) {
        Phone anna = new Phone("Анна", 80);
        Phone boris = new Phone("Борис", 50);
        Phone partner = anna;

        partner.use();
        System.out.println(anna.getBattery());
        System.out.println(boris.getBattery());
        System.out.println(anna == partner);
        System.out.println(Phone.getCreatedCount());
    }
}

class Phone {
    private String model;
    private int battery;
    private static int createdCount;

    Phone(String model, int battery) {
        if (battery < 0 || battery > 100) {
            throw new IllegalArgumentException("Заряд должен быть от 0 до 100");
        }
        this.model = model;
        this.battery = battery;
        createdCount++;
    }

    public void use() {
        if (battery < 10) {
            System.out.println(model + ": недостаточно заряда");
            return;
        }
        battery -= 10;
        System.out.println(model + ": заряд " + battery);
    }

    public int getBattery() {
        return battery;
    }

    public static int getCreatedCount() {
        return createdCount;
    }
}
```

Из папки файла можно выполнить:

```text
javac -encoding UTF-8 OopSummaryDemo.java
java OopSummaryDemo
```

Ожидаемый вывод при отдельном запуске:

```text
Анна: заряд 70
70
50
true
2
```

### Почему именно такие строки

| Инструкция | Что происходит | Что важно не перепутать |
|---|---|---|
| `new Phone("Анна", 80)` | Создаётся первый Phone; конструктор сохраняет данные | Переменная `anna` получает ссылку, а не сам текст класса |
| `new Phone("Борис", 50)` | Создаётся второй Phone со своим зарядом | Одинаковое имя поля не делает заряд общим |
| `Phone partner = anna;` | Копируется значение ссылки | Третий Phone не создаётся |
| `partner.use();` | Вызывается метод первого Phone; заряд 80 превращается в 70 | Объект выбирается по ссылке перед точкой |
| `anna.getBattery()` | Возвращается заряд того же первого Phone | Поэтому ответ 70, хотя действие вызывалось через `partner` |
| `boris.getBattery()` | Возвращается заряд второго Phone | Он остался 50 |
| `anna == partner` | Проверяется, ведут ли ссылки к одному объекту | Это не сравнение всех полей по содержимому |
| `Phone.getCreatedCount()` | Читается общее поле класса | Выполнены два создания Phone, а не три |

Вызов `getBattery()` возвращает число, а внешний `println(...)` печатает его. У `use()` другая ответственность: в этом учебном варианте он меняет состояние и сам сообщает результат. Метод не обязан одновременно делать все три вещи — менять, возвращать и печатать.

### Читаем тело класса по ролям

`private String model` и `private int battery` описывают личные поля экземпляров. У каждого из двух Phone своя пара значений. Имя `model` здесь условное: в примере оно хранит подпись владельца. Его можно согласованно переименовать в `ownerLabel`, чтобы точнее передать смысл.

`private static int createdCount` — общее поле этого загруженного класса. В этом однопоточном опыте оно увеличивается после проверки параметров при каждом нормальном создании Phone. Начальное значение int-поля — 0. Поле не подсчитывает все существующие объекты JVM, строки или массивы.

В `Phone(String model, int battery)` объявлены параметры конструктора. В `this.battery = battery` слева выбран заряд текущего экземпляра, а справа прочитано значение параметра. `this` не является именем, которое придумал программист: так Java обозначает текущий экземпляр в этом контексте.

У `public int getBattery()` тип результата — int, поэтому обычное завершение метода в этом примере передаёт число через `return battery;`. У `public void use()` результата-значения нет; `return;` без числа досрочно завершает только текущий вызов метода.

`public` делает метод доступным с учётом доступности самого класса и других правил доступа. В одном учебном файле `main` может обращаться к непубличному Phone. Для отдельной публичной библиотеки понадобилось бы также продумать доступность класса и его конструктора.

## 5. Зачем ООП, если можно написать всё в main

Для одной короткой формулы отдельный объект может не понадобиться. Польза организации через объекты становится заметнее, когда у программы несколько сущностей и правила их изменения нужно поддерживать во многих местах.

Представь три несвязанных массива: `names`, `batteries`, `prices`. Чтобы описать один телефон, нужно помнить, что одинаковый индекс во всех трёх массивах относится к нему. При ошибочной перестановке одного массива можно связать чужое имя с чужим зарядом.

Класс позволяет хранить связанные данные вместе и дать им подходящие действия. Но само слово `class` не гарантирует хорошую программу: можно создать класс с сотней несвязанных полей и всё равно получить путаницу.

Сначала выясни, какие данные относятся к одной сущности, какие операции с ними разрешены и какие состояния недопустимы. Потом выбирай поля и методы. Например: «заряд не выходит за 0–100, использование расходует 10, при недостаточном заряде состояние сохраняется».

## 6. Инкапсуляция: у состояния есть правила доступа

**Инкапсуляция** связывает состояние с предусмотренными способами работы с ним и позволяет скрыть детали реализации. В нашем примере внешний код не присваивает закрытому `battery` произвольное число; создание и изменение проходят через код класса.

Обрати внимание на две отдельные проверки из первого примера:

```java
if (battery < 0 || battery > 100) {
    throw new IllegalArgumentException("Заряд должен быть от 0 до 100");
}
```

Этот фрагмент находится в конструкторе. Он проверяет входное значение. `||` означает «хотя бы одно условие истинно». При неверном значении `throw` выбрасывает исключение: нормальная инициализация по этому пути не заканчивается. Выражение `new` не возвращает обычный успешно созданный результат для присваивания. Если исключение не обработано, текущий сценарий прерывается.

Второй фрагмент — начало метода `use()`:

```java
if (battery < 10) {
    System.out.println(model + ": недостаточно заряда");
    return;
}
battery -= 10;
```

Здесь уже используется состояние существующего объекта. Если заряда меньше 10, метод сообщает об этом и выходит до вычитания. Если заряда ровно 10, вычитание допустимо и оставит 0. Поэтому отрицательный заряд от этого действия не появляется.

| Начальный заряд | Результат одного use() | Почему |
|---:|---:|---|
| 80 | 70 | Для действия достаточно заряда |
| 10 | 0 | Граница включена: 10 достаточно |
| 9 | 9 | Метод завершился до вычитания |
| 0 | 0 | Нет достаточного заряда |

Условие `0 <= battery && battery <= 100`, которое класс стремится сохранять после завершения разрешённых операций, можно назвать **инвариантом**: правилом допустимого состояния.

`private` само по себе не проверяет числа. Если внутри класса написать неправильное вычитание, ошибка останется. И наоборот, геттер и сеттер для каждого поля не являются обязательной целью. Сеттер, разрешающий любой заряд без проверки, легко разрушит нужное правило.

Инкапсуляция — не шифрование и не защита от любого внешнего вмешательства. Здесь обсуждается устройство программного интерфейса и обычные правила доступа Java.

## 7. Абстракция: выбираем существенное для задачи

**Абстракция** помогает работать с важными для текущей задачи свойствами, не раскрывая каждый внутренний шаг. Когда вызываешь `phone.use()`, можно знать правило расхода заряда, не повторяя этот код в каждом месте программы.

В учебной модели мы учитываем подпись и заряд. Мы не моделируем температуру процессора, каждую микросхему и движение электронов: для обсуждаемой задачи они не нужны. Для другой задачи, например расчёта перегрева, модель потребовала бы других данных.

Абстракция и инкапсуляция связаны, но задают разные вопросы. Абстракция: **что нужно показать пользователю этого класса?** Инкапсуляция: **через какие действия разрешён доступ к состоянию и какие детали скрыты?**

**Контракт** — договорённость о том, как пользоваться классом или методом: какие данные он принимает, что обещает сделать или вернуть и какие ограничения нужно соблюдать. Например, общий контракт `work()` позволяет вызвать действие без аргументов и без возвращаемого значения, а содержательное назначение действия нужно описать дополнительно. Один заголовок не объясняет все правила задачи.

И ещё одно различие: идея абстракции шире слова `abstract`. Даже обычный небольшой класс может давать полезную абстракцию. Ключевое слово `abstract` — конкретный инструмент Java, который появится в следующем примере.

## 8. Наследование: отношение «является разновидностью»

Представь более общую категорию **Device**, то есть «устройство». Phone является разновидностью Device, Laptop тоже является разновидностью Device. У них можно выделить общий способ получить подпись, но действие `work()` у каждого будет своим.

Общая форма объявления:

```text
class ИмяПотомка extends ИмяРодителя {
    объявления особенностей потомка;
}
```

`extends` — слово языка, а оба имени классов выбирает программист. **Родитель**, или **суперкласс**, задаёт общую часть. **Потомок**, или **подкласс**, уточняет её. В рассматриваемой форме класс Java имеет один непосредственный родительский класс. Реализация нескольких интерфейсов — отдельная возможность.

Наследование не означает, что при создании Phone нужно вручную создать ещё один самостоятельный Device и хранить его рядом. Инициализируются части одного экземпляра Phone. Вызов `super(...)` передаёт инициализацию конструктору родителя; он не является вторым `new`.

Конструкторы не наследуются как обычные методы. В нашем примере Phone объявляет свой конструктор и вызывает подходящий конструктор Device. Закрытое поле родителя также нельзя прямо использовать в отдельном классе потомка: для чтения подписи будет доступный метод `getModel()`.

## 9. Полиморфизм: общее обращение, поведение конкретного объекта

Сначала общая форма записи, а затем разберём её на настоящих классах:

```text
Родитель имяСсылки = new Потомок(аргументы);
имяСсылки.общийМетод();
```

В левой части указан тип переменной, а справа создаётся экземпляр конкретного потомка. Присваивание не превращает Phone в самостоятельный объект Device и не удаляет его особенности. Оно позволяет обращаться к Phone через общий тип.

**Полиморфизм** в этом примере означает, что общий вызов экземплярного метода `work()` приводит к реализации, соответствующей фактическому объекту: телефон отправляет сообщение, ноутбук открывает проект.

До запуска компилятор проверяет, что такой вызов разрешён для объявленного типа. Во время выполнения для переопределённого экземплярного метода выбирается реализация по фактическому объекту. Эти два этапа не нужно смешивать.

## 10. Второй опыт целиком: один цикл работает с разными устройствами

Это **отдельная программа в другой папке**, файл **PolymorphismDemo.java**. Класс Phone здесь имеет другую учебную реализацию. Не объединяй этот файл и первый опыт с ещё одним Phone в одном пакете: имена классов столкнутся.

Во втором опыте мы специально убрали заряд и счётчик. Теперь сосредоточимся на общей категории и разных реализациях одного действия. Результаты первого опыта от этого не меняются.

```java
public class PolymorphismDemo {
    public static void main(String[] args) {
        Device[] devices = {
            new Phone("Телефон"),
            new Laptop("Ноутбук")
        };

        for (Device device : devices) {
            device.work();
        }
    }
}

abstract class Device {
    private String model;

    Device(String model) {
        this.model = model;
    }

    public String getModel() {
        return model;
    }

    public abstract void work();
}

class Phone extends Device {
    Phone(String model) {
        super(model);
    }

    @Override
    public void work() {
        System.out.println(getModel() + ": отправлено сообщение");
    }
}

class Laptop extends Device {
    Laptop(String model) {
        super(model);
    }

    @Override
    public void work() {
        System.out.println(getModel() + ": открыт проект");
    }
}
```

Команды из папки второго опыта:

```text
javac -encoding UTF-8 PolymorphismDemo.java
java PolymorphismDemo
```

Ожидаемый вывод:

```text
Телефон: отправлено сообщение
Ноутбук: открыт проект
```

### Что означает каждое новое обозначение

| Запись | Объяснение |
|---|---|
| `abstract class Device` | Общий абстрактный класс. Непосредственное `new Device(...)` запрещено |
| `private String model` | Поле состояния; оно есть в каждом из созданных экземпляров с родительской частью Device |
| `Device(String model)` | Конструктор общей части экземпляра; абстрактный класс может иметь конструктор |
| `getModel()` | Обычный метод с готовым телом; возвращает подпись |
| `public abstract void work();` | Объявление действия без тела. Здесь стоит `;`, а не пустой блок `{}` |
| `extends Device` | Объявление отношения наследования |
| `super(model)` | Передача аргумента конструктору родителя; сохраняется подпись этого экземпляра |
| `@Override` | Аннотация, то есть специальная пометка в коде: просим компилятор проверить, что метод действительно переопределяет подходящее объявление |
| `public void work() { ... }` в Phone | Конкретная реализация действия телефона |
| `Device[]` | Массив ссылок, допускающий в этом примере Phone и Laptop как разновидности Device |
| `Device device` в for-each | Переменная очередной итерации с общей ссылкой, а не создание нового устройства |

`abstract` и `extends` нельзя переименовать. Имя `Device`, имя `work` и имя параметра `model` выбирает автор, но связанные объявления и вызовы нужно менять согласованно. `@Override` — существующая аннотация Java, её название тоже не заменяют придуманным словом.

В наших примерах `super(...)` стоит первой инструкцией конструктора: такой вариант подходит и для Java 17/21. Более новые версии допускают дополнительные формы тел конструкторов; для этого опыта они не нужны.

У абстрактного класса могут быть поля, конструктор, обычные методы и абстрактные методы. Он не является «классом вообще без кода». Конкретный неабстрактный подкласс должен предоставить нужные реализации или унаследовать подходящие готовые реализации.

### Тип переменной ограничивает доступные обращения

Для фрагмента внутри `main`:

```java
Device device = new Phone("Учебный");
device.work();
```

Фактический объект — Phone, а тип переменной — Device. Если позднее только в Phone появится метод `call()`, запись `device.call()` сама по себе не станет допустимой: у объявленного типа Device такого метода нет. Общий тип позволяет пользоваться общей частью контракта.

Обычный вызов `work()` не требует вручную проверять каждый вариант через цепочку `if (это Phone) ... else if (это Laptop) ...`. Выбор подходящей переопределённой реализации уже выполняет механизм вызова экземплярного метода.

В эту модель не следует автоматически переносить поля, конструкторы, перегрузку и статические методы. Для них действуют другие правила; в частности, `static`-методы не переопределяются как экземплярный `work()`.

## 11. Четыре идеи ООП рядом

| Идея | На какой вопрос отвечает | Где видно в опытах |
|---|---|---|
| **Инкапсуляция** | Как сохранять допустимое состояние и управлять доступом? | Закрытый заряд и проверенное действие `use()` |
| **Абстракция** | Что существенно и какой общий контракт нужен? | Работать с устройством через понятное действие `work()` |
| **Наследование** | Является ли один тип разновидностью другого? | `Phone extends Device`, `Laptop extends Device` |
| **Полиморфизм** | Как одинаковое обращение работает с разными реализациями? | Один цикл вызывает разный `work()` по фактическим объектам |

Такой набор часто называют четырьмя основными идеями ООП. Это удобная учебная карта, а не требование использовать все четыре механизма в каждом маленьком классе. Хороший первый Phone уже полезен без наследования и абстрактного класса.

Интерфейс — ещё один инструмент задания общего контракта. Через него тоже можно организовать полиморфные вызовы. Но абстракция не сводится только к интерфейсам, а полиморфизм не требует именно абстрактного родителя. Здесь выбран один понятный вариант для первого знакомства.

## 12. Не путай похожие слова и записи

| Похоже внешне | Различие по смыслу |
|---|---|
| `Phone partner = anna` и `new Phone(...)` | Первое копирует ссылку, второе создаёт новый экземпляр Phone |
| `private` и проверка диапазона | Первое управляет доступом, второе проверяет данные |
| Абстракция и `abstract` | Первое — идея проектирования, второе — конкретное слово Java |
| Перегрузка и переопределение | Перегрузка различает варианты метода по параметрам; переопределение меняет реализацию унаследованного экземплярного метода с подходящей сигнатурой |
| `return` и `println` | Первое отдаёт результат или завершает вызов; второе выводит текст |
| Поле экземпляра и `static`-поле | Первое относится к конкретному экземпляру; второе общее для соответствующего загруженного класса |
| `this` и `super(...)` | В примерах первое обращается к текущему экземпляру, второе вызывает конструктор родителя |
| Наследование и копирование кода | Наследование задаёт отношение типов и правила доступа; это не просто вставка текста одного файла в другой |

## 13. «Является» и «содержит»: не всё нужно наследовать

Телефон **является устройством**, но телефон **содержит аккумулятор**. Из фразы «телефон имеет аккумулятор» не следует `Phone extends Battery`: телефон не является разновидностью аккумулятора.

**Композиция** — организация объекта через связанные части. В обычном широком обсуждении так называют подход «содержит»; в строгой UML-модели композицией называют более сильную связь владения и жизненного цикла. UML — язык схем для описания программных моделей. Точные правила такой связи заданы в [спецификации UML](https://www.omg.org/spec/UML/2.5.1/PDF). Одного поля-ссылки недостаточно, чтобы доказать такую строгую связь.

Общая идея поля-компонента выглядит так; это набросок структуры, а не новая готовая программа:

```text
class Телефон {
    private Аккумулятор аккумулятор;
}
```

Нужно ещё объявить класс компонента, создать или передать его экземпляр и решить, кто им владеет. Значение `null` в поле само по себе не создаст аккумулятор.

Выбирая наследование, спроси: «Можно ли в этой задаче использовать потомка там, где ожидают родителя, сохраняя обещанное поведение?» Сходства двух полей или желания сократить несколько строк недостаточно. Если связь описывается словами «использует» или «содержит», сначала рассмотри отдельный компонент.

## 14. Как прочитать незнакомую программу с объектами

1. Найди точку входа: откуда начинается рассматриваемый сценарий.
2. Отдельно выпиши объявления классов. Само положение метода ниже в файле не задаёт очередь его исполнения.
3. Найди выражения `new` и отметь создания нужных экземпляров. Укажи их типы и начальные данные.
4. Рисуй переменные отдельно от объектов. Присваивание ссылки меняет значение переменной, а не создаёт копию объекта.
5. Перед каждым экземплярным вызовом определи получателя: что стоит перед точкой и к какому объекту ведёт эта ссылка.
6. Для переопределённого метода различай тип переменной и фактический класс объекта.
7. Отмечай изменение конкретных полей, возвращаемое значение и вывод отдельно.
8. Для `static`-поля отдельно веди общее значение, не дублируй его по всем объектам на рисунке.

Потеря последней достижимой ссылки может сделать объект доступным для сборки мусора; немедленное уничтожение в этот момент не гарантируется. Счётчик созданий из первого опыта автоматически не уменьшается. Java передаёт аргументы по значению, включая копии значений ссылок: появление параметра не создаёт особого режима «передачи объекта по ссылке».

## 15. Проверь понимание на изменениях

### Задание А. Ссылки и состояние

В первом опыте замени `Phone partner = anna;` на `Phone partner = boris;`. Не меняй остальные строки. Сначала предскажи вывод, затем проверь.

Ожидается: сообщение о заряде Бориса 40, затем числа 80 и 40, затем `false`, затем 2. Если получился другой результат, покажи на рисунке, к какому объекту ведёт `partner` именно перед `use()`.

### Задание Б. Граница допустимого действия

Проверь первый Phone с зарядом 10, затем 9. В первом случае один `use()` оставит 0, во втором сохранит 9. Затем проверь -1 и 101: конструктор должен выбросить исключение. Каждый опыт запускай отдельно или явно обрабатывай исключение; иначе первое необработанное исключение прервёт последующие шаги.

### Задание В. Новая реализация общего действия

Во втором опыте добавь `Tablet extends Device`. Его `work()` должен печатать подпись и текст «открыта книга». Добавь `new Tablet("Планшет")` третьим элементом массива. Сам цикл оставь тем же: должна появиться третья строка вывода.

Если компилятор говорит, что метод не переопределяется, сравни имя, параметры и доступность. Метод `work(int minutes)` — другая перегрузка, он не заменяет требуемый `work()` без параметров.

## 16. Что означает «основы усвоены»

Базовый результат — уметь придумать простой класс, обосновать его поля и действия, создать два независимых экземпляра, объяснить копирование ссылки, использовать конструктор и выбрать между личными и общими данными. После этой лекции к этому добавляется начальное понимание общего типа и разных реализаций действия.

Дальнейший маршрут: подробнее изучить наследование и правила доступа, переопределение и `super`, интерфейсы и абстрактные классы, работу с исключениями, коллекциями и контрактами `equals`/`hashCode`. Эти темы расширяют модель, а не отменяют правила ссылок и состояния.

Главный навык — объяснять, **какие объекты существуют, кто может к ним обратиться, какие действия разрешены и что именно изменяется после вызова**. Если это получается на небольшом примере без угадывания, основа для следующих тем готова.
